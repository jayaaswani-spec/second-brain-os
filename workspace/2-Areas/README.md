# 2-Areas

Thin **Area workstations** — one folder per long-running area of responsibility. This is the "A" in PARA.

## Purpose

An Area is the standing context for one ongoing area of responsibility: its rules, its working memory and a list of its projects. Unlike a project, it has no "done" state and is owned indefinitely. **Areas are thin: they never hold content.** Docs, playbooks, decks and data live in the Area's projects (`1-Projects/` while active, `5-Archive/` when done).

Each Area lives at `<workspace.root>/2-Areas/<name>/` and holds exactly:

```
2-Areas/<name>/
├── CLAUDE.md      # the Area's rules, voice + routing triggers (no content)
├── memory.md      # the Area's working memory
├── index.md       # generated list of projects with parent_hq: <name>, live + archived
└── apps/          # optional: shipped apps the Area owns (each gitignored, own git)
```

`index.md` is regenerated by `/reindex`; never hand-edit it.

**This folder is empty on a fresh fork.** You don't need it on day one. Areas emerge as your work develops recurring, long-running threads — a client, a program, a product line, a team you support.

## Project vs Area — the distinction

| | `1-Projects/` | `2-Areas/` |
|---|---|---|
| Lifespan | Time-bound, has a "done" | Evergreen, never "done" |
| Example | "Q3 pricing redesign" | "Pricing & packaging" (the ongoing area) |
| On completion | Archived whole to `5-Archive/` | Its `index.md` keeps linking the archived project |
| Frontmatter | `status: active\|done` | n/a (always live) |

A project names its parent area with `parent_hq:` frontmatter (the bare Area name, e.g. `parent_hq: pricing`). When the project completes, `/archive-project` moves it whole to `5-Archive/` and regenerates `2-Areas/pricing/index.md`. Nothing is promoted into the Area.

## What belongs here

- ✓ "Client X" — an account you support across many projects over time
- ✓ "Hiring" — the ongoing function; each req or playbook rewrite is a project under it
- ✓ "Newsletter" — a recurring publication; its voice rules live here, each edition is a project
- ✓ "Platform team" — a group you partner with indefinitely

What goes inside the folder is only the rules, memory and index above, plus `apps/` for software the Area owns.

## What doesn't belong here

- ✗ A bounded deliverable with a deadline → `1-Projects/`
- ✗ Docs, playbooks, decks or data → a project in `1-Projects/` (with `parent_hq:` set)
- ✗ A one-off reference doc or saved article → `4-Resources/`
- ✗ A code repo still being built → a `COD-` project's `app/` (only shipped, maintained apps live in `<area>/apps/`)
- ✗ A half-formed idea → `0-Inbox/`

## Area routing (progressive context loading)

Once you have Areas, **don't pre-load them all** at session start — that bloats context. Keep a routing-map table in your root `memory.md` mapping task type → Area. At the start of each turn, match the task and load **only** the matched Area's `CLAUDE.md` + `memory.md`. When nothing matches, work from root context alone. The Area model in root `CLAUDE.md` documents this in full.

## How `<assistant.name>` uses this folder

- Reads the matched Area's `CLAUDE.md` + `memory.md` when a task routes to it
- Regenerates the Area's `index.md` (`/reindex`) when a project with `parent_hq:` pointing here is created or archived

## Creating an Area

There's no dedicated skill — an Area is a deliberate decision, not a scaffold. When a workstream has clearly earned evergreen status:

1. `mkdir 2-Areas/<name>/` with `CLAUDE.md` + `memory.md`, then run `/reindex` on it to generate `index.md`
2. Write the Area's rules + routing triggers into its `CLAUDE.md`
3. Add a row to the routing-map table in root `memory.md`
4. Point relevant projects at it via `parent_hq: <name>`
