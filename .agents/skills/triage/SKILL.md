# Triage

Move tickets on the project's tracker through a small state machine of triage roles. The work can be code or knowledge work.

Resolve the project and its paths from `docs/agents/project-context.md`. If a skill earlier in this conversation already resolved them, reuse that.

Every comment posted during triage **must** start with this disclaimer:

```
> *This was generated by AI during triage.*
```

## Reference docs

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — how to write durable agent briefs
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — how rejected requests are recorded and matched later

## Roles

The **category** is the ticket's type:

- `Bug` — something is broken
- `Story` — a new capability or deliverable
- `Task` — prep, setup, cleanup, an approval step, anything that isn't new capability

Five **state** roles:

- `needs-triage` — maintainer needs to evaluate
- `needs-info` — waiting on the requester for more information
- `ready-for-agent` — fully specified, ready for an AFK agent
- `ready-for-human` — fully specified, but a person has to do it
- `wontfix` — will not be actioned

Every triaged ticket should carry exactly one category and one state: the `**Type:**` and `**Status:**` lines of the ticket file. If the state looks contradictory (for example a Won't fix ticket with open work under it), flag it and ask the maintainer before doing anything else.

State transitions: an untriaged ticket normally goes to `needs-triage` first; from there it moves to `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`. `needs-info` returns to `needs-triage` once the requester replies. The maintainer can override at any time — flag transitions that look unusual and ask before proceeding.

## Invocation

The maintainer invokes `/triage` and describes what they want in natural language. Interpret the request and act. Examples:

- "Show me anything that needs my attention"
- "Let's look at ticket 04"
- "Move ticket 04 to ready-for-agent"
- "What's ready for agents to pick up?"
- "Triage ticket 04 in the second-brain project"

## Show what needs attention

Query the tracker and present these buckets, oldest first:

1. **Needs triage** — evaluation in progress.
2. **Needs info with requester activity since the last triage notes** — needs re-evaluation. A ticket qualifies when someone added a note after the latest `## Triage` entry. A triage entry is recognised by the disclaimer at the start of its text. Order this bucket by the oldest unanswered reply. Needs info tickets with no new reply get a one-line count, not a listing.
3. **Never triaged** — ticket files with no `**Status:**` line. Show the count and the oldest three, not the full list. Work through them only when the maintainer asks.

Read the `**Status:**` line of every ticket file in the project.

If a ticket carries a date the requester asked for, say so on its line.

Show counts and a one-line summary per item. Let the maintainer pick.

## Triage a specific ticket

1. **Gather context.** Read the full ticket: description, comments, type, status, reporter, parent spec, blockers, dates. Parse any prior triage notes so you don't re-ask resolved questions. Explore the work using the project's own vocabulary (`CONTEXT.md` or `glossary.md`), respecting its recorded decisions. Run two checks:
   - **(a) Redundancy.** Search for existing work that already does what's asked, by concept, not just the request's wording: the project folder, then `/find` across the workspace, and the code repo when the request is about code. Report where you looked. If found, it's an already-done `wontfix` (step 5).
   - **(b) Prior rejection.** Read past rejections in the project's `out-of-scope/` folder and surface any that resembles this request, per [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md). A decision already recorded in the project's `memory.md` or `decisions/` that rules the request out counts too; surface it the same way.

2. **Recommend.** Tell the maintainer your category and state recommendation with reasoning, plus a brief summary of the relevant current state — including whether it's already done. When verification is cheap (reading a page, checking a ticket), do step 3 first and include the result. Wait for direction.

3. **Verify the claim.** Before any grilling, check that the claim holds up.
   - **Bug:** reproduce it from the reporter's steps. For a connector or app, try it through its own tools or UI, never by calling its upstream API directly.
   - **Knowledge work:** check the facts the request rests on: the doc, page, data or person it names exists and says what the request says it does.

   Report what happened: confirmed (with the path through the system), failed, or insufficient detail (a strong `needs-info` signal). A confirmed verification makes a much stronger agent brief.

   If the maintainer already decided the outcome after the recommendation (a rejection, an override), skip verification and grilling and go to step 5.

4. **Grill (if needed).** If the request needs fleshing out, run the `/grilling` and `/domain-modeling` skills together — grill it into shape one question at a time, sharpening domain terms and updating the glossary and decision records inline as decisions land.

5. **Apply the outcome.** Show the maintainer the exact change first: the status move, the comment text, any link or type change. Write only after they approve. Then:
   - `ready-for-agent` — post an agent brief comment ([AGENT-BRIEF.md](AGENT-BRIEF.md)). The status tells an agent it can pick the ticket up.
   - `ready-for-human` — same structure as an agent brief, but note why it can't be delegated (judgment calls, access an agent doesn't have, design decisions, sign-off, manual testing).
   - `needs-info` — post triage notes (template below).
   - `wontfix` — close, with the comment depending on *why*:
     - **Already done** — the work already exists. Point to where it lives (a ticket, a doc, a repo). Do **not** record it as a rejection; that record is for *rejected* requests, not finished ones.
     - **Rejected (Bug)** — polite explanation, then close.
     - **Rejected (Story or Task)** — record the rejection per [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md), then close. The comment links to the `out-of-scope/` file.
     - **Repeat of an earlier rejection** — once the maintainer confirms the match, add this ticket to the original `out-of-scope/` file's "Prior requests" list, comment with the original's reason and a link to that file, then close.

     If the maintainer gives the decision but not the reasoning, draft the reason from what's on record and put it in the preview for approval. Never invent facts to fill it out.
   - `needs-triage` — apply the state. Optional comment if there's partial progress.

   Moving a ticket to `ready-for-agent` or `ready-for-human` also brings it up to the ticket template in `to-tickets`: the `**Type:**` and `**Blocked by:**` lines and the labelled lines its type needs. Propose anything missing in the same approval. A vague `Done when:` or acceptance line may be tightened into something checkable, shown in the same preview. A ticket closing as Won't fix keeps its lines as they are; only its type changes, and only if it's clearly wrong.

   A deferral ("not now, maybe in Q1") is not a rejection: it keeps its status and gets a triage note saying what would bring it back.

### Writing a local ticket

- Update the `**Status:**` line.
- Append the comment under a `## Triage` heading at the end of the ticket file. Each entry starts with a dated `### YYYY-MM-DD` line, then the disclaimer, then the comment; newest last. Link project files as wikilinks (`[[../out-of-scope/dark-mode]]`).
- A Won't fix ticket stays in `tickets/` with `**Status:** wontfix`; don't delete or move it.

## Quick state override

If the maintainer says "move ticket 04 to ready-for-agent", trust them and apply the state directly. Confirm what you're about to do (status change, comment, close), then act. Skip grilling. If moving to `ready-for-agent` without a grilling session, ask whether they want to write an agent brief.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@requester):**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so the work isn't lost. Questions must be specific and actionable, not "please provide more info".

## Resuming a previous session

If prior triage notes exist on the ticket, read them, check whether the requester has answered any outstanding questions, and present an updated picture before continuing. Don't re-ask resolved questions.
